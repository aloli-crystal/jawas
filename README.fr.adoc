= jawas
:toc: left
:toc-title: Sommaire

Couteau suisse de sauvegarde, écrit en Crystal : dumps MySQL/MariaDB,
PostgreSQL et SQLite, rotation quotidienne/hebdomadaire/mensuelle,
compresseur au choix, empreintes SHA-256, configuration TOML.

`jawas` reprend les principes
https://sourceforge.net/projects/automysqlbackup/[d'automysqlbackup]
(rotation daily/weekly/monthly, une archive par base, hooks avant/après)
et les élargit : plusieurs moteurs, plusieurs serveurs dans une même
configuration, chiffrement `age` à clés publiques, vérification et
restauration des sauvegardes, et une feuille de route vers l'envoi
distant.

English version: link:README.adoc[README.adoc].

== Fonctionnalités (0.3.0)

* *Moteurs* : MySQL et MariaDB (`mysqldump` / `mariadb-dump`),
  PostgreSQL (`pg_dump`, SQL ou format `custom`, plus les rôles via
  `pg_dumpall --globals-only`), SQLite (copie à chaud cohérente via
  `.backup`, ou dump SQL).
* *Plusieurs sources* par configuration (`[[source]]`), découverte
  automatique des bases, exclusions par motif (`test_*`) et par table.
* *Rotation* : chaque exécution alimente `daily` ; le jour choisi, le
  même fichier est lié (hardlink, zéro octet de plus) dans `weekly`
  et/ou `monthly`. Durées en jours par période et plancher `keep_min`
  qui empêche une panne prolongée de vider le stockage.
* *Compression* en flux : `none`, `gzip`, `pigz`, `bzip2`, `xz`,
  `zstd`, avec niveau et threads.
* *Chiffrement* `age` (0.2) : après la compression, vers une ou
  plusieurs clés publiques (`age1…`, `ssh-ed25519`, `ssh-rsa`) en ligne
  ou dans un fichier `age -R`. Le serveur ne détient aucune clé privée :
  il ne peut pas relire ses propres sauvegardes.
* *Vérification et restauration* (0.3) : `verify` contrôle empreinte,
  archive et contenu ; `restore` recharge une sauvegarde, par défaut
  dans une base jetable.
* *Intégrité* : écriture dans un `.part` puis renommage atomique,
  fichier `.sha256` (format `sha256sum -c`), fichiers en 0600 et
  répertoires en 0700, lien `latest/` vers le dernier dump.
* *Sécurité des identifiants* : aucun mot de passe en clair dans la
  configuration ni en ligne de commande (`password_env`,
  `password_file`, `defaults_file`).
* *Exploitation* : verrou contre les exécutions concurrentes, hooks
  `pre`/`post`, rapport JSON `last-run.json`, codes de sortie
  exploitables par la supervision.

== Installation

[source,shell]
----
git clone git@github.com-aloli:aloli-crystal/jawas.git
shards build --release --production
ln -s "$PWD/bin/jawas" ~/bin/jawas
----

Outils externes, selon les moteurs et le compresseur utilisés :
`mysqldump`/`mariadb-dump`, `pg_dump`/`pg_dumpall`/`psql`, `sqlite3`,
`gzip`/`pigz`/`bzip2`/`xz`/`zstd`, et `age` (ou `rage`) pour le chiffrement.

== Démarrage rapide

[source,shell]
----
jawas sample > ~/.config/jawas/config.toml
jawas check
jawas backup
jawas backup --apply
jawas list
----

`backup` et `prune` sont en *dry-run* par défaut : ils affichent ce
qu'ils feraient. `--apply` (`-a`) exécute réellement. Exemple de ligne
cron :

[source]
----
15 3 * * *  /usr/local/bin/jawas backup --apply --quiet
----

== Configuration

Recherche dans l'ordre : `--config CHEMIN`,
`${XDG_CONFIG_HOME:-~/.config}/jawas/config.toml` (ignoré avec
`--no-user-config`), `/etc/jawas/config.toml`,
`/usr/local/etc/jawas/config.toml`. `jawas sample` affiche un modèle
complet et commenté. Les clés inconnues sont refusées (pas de faute de
frappe silencieuse).

[source,toml]
----
[storage]
dir = "/var/backups/jawas"

[schedule]
weekly_day = 6        # samedi (1 = lundi … 7 = dimanche)
monthly_day = 1

[retention]           # jours
daily = 7
weekly = 35
monthly = 180
keep_min = 2

[compression]
tool = "zstd"
level = 6

[encryption]
recipients = ["age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p"]

[[source]]
name = "mariadb"
engine = "mariadb"
socket = "/run/mysqld/mysqld.sock"
user = "backup"
password_file = "/etc/jawas/mariadb.password"

[[source]]
name = "pg"
engine = "postgresql"
socket = "/var/run/postgresql"
user = "postgres"
----

== Chiffrement et relecture

La section `[encryption]` active le chiffrement ; sans elle, les
sauvegardes restent en clair. Les fichiers prennent l'extension `.age`
après celle du compresseur (`app_….daily.sql.zst.age`) et la somme
`.sha256` porte sur le fichier chiffré. `jawas check` vérifie que `age`
accepte chaque destinataire.

[source,toml]
----
[encryption]
recipients = ["age1…", "ssh-ed25519 AAAA… ops@poste"]
recipients_file = "/usr/local/etc/jawas/recipients.txt"   # une clé par ligne
# binary = "rage"
----

Créer la paire de clés sur le poste de l'opérateur (jamais sur le
serveur), puis relire une sauvegarde :

[source,shell]
----
age-keygen -o ~/.config/age/jawas.txt
age -d -i ~/.config/age/jawas.txt app_2026-11-16_03h15.daily.sql.zst.age | zstd -dc > app.sql
----

Conservez la clé privée en lieu sûr (et une copie de secours) : sans
elle, les sauvegardes chiffrées sont perdues.

== Vérification et restauration

`jawas verify` contrôle, par défaut, la dernière sauvegarde de chaque
base (`-A` : toutes), à trois niveaux :

0. *empreinte* : le fichier correspond à son `.sha256` ;
0. *archive* : il se déchiffre (avec `-i`) et se décompresse jusqu'au
   bout ;
0. *contenu* : le dump est complet (marque de fin de `mysqldump` ou de
   `pg_dump`, en-tête `PGDMP`, `COMMIT;` final ou
   `PRAGMA integrity_check` pour SQLite).

Sans `-i`, une sauvegarde chiffrée n'est contrôlée que sur son
empreinte (« partielle »). Le code de sortie vaut `2` si un contrôle
échoue : `jawas verify -q` se prête à une tâche planifiée.

[source,shell]
----
jawas verify
jawas verify -A -i ~/.config/age/jawas.txt
----

`jawas restore` recharge une sauvegarde. Sans `--apply`, il affiche la
sauvegarde choisie et la cible. Par défaut :

* la sauvegarde est la plus récente de la base (`-D AAAA-MM-JJ` : la
  plus récente de ce jour ; `-f` : un fichier précis) ;
* la cible est une *base jetable* `<base>_r<AAAAMMJJHHMM>` sur le même
  serveur (SQLite : fichier voisin `<base>.r<AAAAMMJJHHMM>.sqlite3`),
  à inspecter puis supprimer.

[source,shell]
----
jawas restore -d app
jawas restore -d app --apply
jawas restore -s pg -d app -D 2026-11-14 -t app_hier --apply
jawas restore -d app -t app -R -i ~/.config/age/jawas.txt --apply
----

Garde-fous :

* l'empreinte SHA-256 est contrôlée avant tout chargement ;
* une cible existante n'est écrasée qu'avec `-R/--replace` ; écraser la
  base d'origine exige donc `-t <base> -R --apply`. Pour MySQL et
  PostgreSQL, la base est supprimée puis recréée : restaurez d'abord
  dans une base jetable pour vérifier. SQLite est remplacé d'un bloc
  (fichier renommé après `PRAGMA integrity_check`) ;
* une base jetable créée pour une restauration qui échoue est supprimée ;
* `_globals` (rôles PostgreSQL) se rejoue à la main : décoder le
  fichier, puis `psql -d postgres -f -`.

Le chargement passe par `mysql`/`mariadb` (en-tête `CREATE DATABASE`
et `USE` retiré pour viser la cible), `psql -v ON_ERROR_STOP=1` ou
`pg_restore --exit-on-error`, et `sqlite3`.

== Arborescence produite

[source]
----
/var/backups/jawas/
├── mariadb/
│   ├── daily/app/app_2026-11-16_03h15.daily.sql.zst
│   ├── daily/app/app_2026-11-16_03h15.daily.sql.zst.sha256
│   ├── weekly/app/…            (liens physiques)
│   ├── monthly/app/…
│   └── latest/app.sql.zst → ../daily/app/app_2026-11-16_03h15.daily.sql.zst
├── pg/…
└── last-run.json
----

Avec `[encryption]`, les noms se terminent par `.age`
(`app_2026-11-16_03h15.daily.sql.zst.age`, `latest/app.sql.zst.age`).

== Commandes

[cols="1,1,4"]
|===
| Commande | Court | Rôle

| `backup` | `b` | Dumps, liens, rotation, rapport (dry-run sans `--apply`)
| `prune`  | `p` | Rotation seule (dry-run sans `--apply`)
| `list`    | `l` | Inventaire des sauvegardes du stockage
| `verify`  | `v` | Contrôle empreinte, archive et contenu
| `restore` | `r` | Restauration, base jetable par défaut (dry-run sans `--apply`)
| `check`  | `c` | Configuration, exécutables, stockage, connexions
| `sample` | `s` | Modèle de configuration
| `help`   | `h` | Aide globale ou `help <commande>`
|===

Options : `-c/--config`, `-U/--no-user-config`, `-a/--apply`,
`-s/--source` et `-d/--database` (répétables ou `a,b`),
`-P/--no-prune`, `-j/--json`, `-q/--quiet`, `-v/--version`,
`-h/--help` ; pour `verify` et `restore` : `-i/--identity` (clé privée
age), `-A/--all`, `-D/--date`, `-f/--file`, `-t/--into`,
`-R/--replace`.

Codes de sortie : `0` succès, `1` usage ou configuration, `2` au moins
une base en échec, `3` verrou tenu par une autre exécution.

== Différences avec automysqlbackup

* Configuration TOML validée au lieu d'un fichier shell sourcé.
* Une exécution = une série `daily` continue ; weekly/monthly sont des
  liens physiques au lieu de dumps séparés.
* Rétention avec plancher `keep_min`.
* Pas de mot de passe dans la configuration (fichier d'options 0600
  temporaire pour MySQL, `PGPASSWORD` pour PostgreSQL).
* Chiffrement `age` à clés publiques au lieu d'`openssl` à mot de
  passe partagé.
* Pas encore d'envoi de rapport par mail ni de mode différentiel :
  voir la feuille de route.

== Feuille de route

0. *0.2* — chiffrement `age` (destinataires multiples) : livré.
0. *0.3* — `verify` et `restore` : livrés.
0. *0.4* — envoi distant (SFTP/rsync, stockage objet S3 : OVH,
   Scaleway…), notification mail/webhook du rapport.
0. *0.5* — politique de rétention GFS fine, métriques pour la
   supervision.
0. Ensuite — sources « fichiers » (rsync, archives tar), au-delà des
   bases de données.
